**What the baseline says (next work, in order)**
1. *Full view 12-20 s, and contacts vanish when sub-pixel*. This is the Phase 2 density pyramid

2. *Load 337 s for 3.9 GB*. The stream decode is serial; independent CBLOCKs and a sidecar of

3. *Resident 14 GB for 10L*. Mmap'd compact tiles from the disk cache and decode-on-demand

4. *Draw on real hardware*. Needs a machine with a display and GPU (or EGL on the NVIDIA

**Phase 2: strict-mode open + sidecar (done)**

- **Sidecar `<file>.oas.mvi`.** `src/db/oasis_sidecar.cpp`, C API `ldb_mvi_*`. It holds:
  - one entry per unit: a top-level CBLOCK, or a run of inline records split at CELL records and every 4 MB;
  - per (unit, layer) box counts and bboxes;
  - modal snapshots for units whose decode depends on earlier modal state;
  - a per-layer density pyramid: 1024 tiles on the longer side, box counts plus clipped covered area, 2x2-reduced levels.
- **How the build works.** Each unit is decoded speculatively in parallel, starting with every modal variable undefined. The parser (`src/db/oasis_parser.hpp`, shared with `oasis.cpp`) throws on the first use of an undefined variable. A sequential pass then fixes up the true state, re-decodes the dependent units and saves their snapshots.
- **Validity and location.** The sidecar is validated against the OASIS file's size and mtime. If the input directory is read-only, it is written to `$MAGVIEWER_CACHE_DIR` or `$TMPDIR`.
- **Fallback.** Hierarchical files fall back to the Phase 1 loader. The sidecar handles flat files only.
- **Tools:**
  - `db/db_mvi build|info|check|bench`. `check` decodes every layer from the sidecar and compares count and an order-free hash with the streaming parser.
  - `test_layout_files.exe file.oas [windows] [frac]`: Fortran API test. Tiled windows are checked against a brute-force oracle.
- **Viewer** (`MAGVIEWER_SIDECAR=1`, the default for OASIS without `--hier`; code in `viewer_tiles.f90`, type `TiledLayout`). It opens instantly and picks a mode per frame:
  - **density:** a CPU-composited image of the pyramid for all visible layers;
  - **geometry:** used when the pyramid estimate of boxes in view is at most `MAGVIEWER_FRAME_BOXES` (default 3M), with 2x hysteresis. It decodes the units the view touches into a tile LRU (`MAGVIEWER_CACHE_GB`, default 4). Sub-pixel boxes are drawn 1 px wide.
  - The minimap is a density image of the whole design.
  - `MAGVIEWER_VIEW=x1,y1,x2,y2` (um) sets the start view.
- **Fortran front end** (`layout_files.f90`, `LayoutFilesModule`): `LayoutFile`, `OasisTables`, `LayoutSidecar` own the C handles, with finalizers. Julia: `src/db/julia/LayoutDB`.

**Results.**
- All MW_8x8 units are independent: 0 dependent units. The KLayout-written `kl_strict.oas` has 18 dependent units, and its snapshots decode exactly.
- `db_mvi check` on 10L (4.1 B boxes, every layer) matches the streaming parser, at 430–730 Mbox/s.

**Open issues (Phase 3 work).** Geometry frames on 10L at 0.61 um/px have 2–5 s query and 1–5 s software-GL draw (1–5 M boxes). A view touches 30–70 units of about 2 M boxes each, so decode is far larger than the view, and the 4 GB tile LRU churns. The fixes are smaller decode units (per-bin sub-units in the sidecar, or compact tiles in a disk cache), decode-ahead on a worker thread, and GPU draw (Phase 5).

## 2. Goals and targets

1. **Strict-mode OASIS loads in time proportional to the screen, not the file.** First frame of
   any file, including 1 TB, in < 2 s: read START/END, the table offsets, the CELLNAME table
   with `S_CELL_OFFSET` / `S_BOUNDING_BOX`, and draw the top-cell bbox plus a coarse density map.
   Geometry is decoded only for what the view needs.
2. **Bounded memory.** Resident viewer memory set by a budget (`MAGVIEWER_MEM_GB`, default
   4 GB host + 2 GB GPU), independent of file size. Decoded data lives in an LRU memory cache
   backed by an on-disk cache on NVMe.
3. **GPU where it pays:** CBLOCK inflate (nvCOMP batched, when it beats the CPU), density-map
   build, spatial-index (LBVH) build from Morton keys, and rendering straight from compact
   blocks in a shader.
4. **True geometry:** rectangles, trapezoids/CTRAPEZOIDs and polygons (MULTIGON, see §11)
   drawn as their real shapes, not their bboxes.
5. **Usable UI:** layer names (`LAYERNAME` or `67/20`), `?` help on the terminal, a
   performance HUD, a ruler, shape picking with properties (net id/name, metrology), and
   annotations.
6. **Reproducible benchmarks** on MW_8x8 (flat, 1 / 5 / 10 layers, strict mode, cell bbox):
   load, first frame, pan/zoom frame times, memory, with KLayout as a reference point.

### A note on "1 TB, > 10 trillion shapes"
10T shapes in 1 TB is 0.1 B/shape. Our best flat encoding is 0.24 B/box (sorted RECTANGLE
records with modal width/height and CBLOCKs), so a **flat** 1 TB file holds roughly 4T boxes.
Reaching 10T needs hierarchy and/or OASIS repetitions. The design therefore must never
flatten: it renders hierarchy through cell bboxes and expands placements and repetitions
lazily, only for the view. Flat files (MW_8x8) and hierarchical files take the same path; a
flat file is just one cell with very many CBLOCKs.

## 3. Architecture

```
               +-------------------- OASIS file (mmap, read-only) --------------------+
               | START | tables (CELLNAME+S_CELL_OFFSET+S_BOUNDING_BOX, LAYERNAME, ...) |
               | CELL a: CBLOCK CBLOCK ... | CELL b: ... |  END (table offsets)        |
               +------------------------------------------------------------------------+
                        |                                   |
     (1) open: tables only, < 1 s            (2) one-time scan (background, resumable)
                        |                                   |
                        v                                   v
         Cell table: name, offset, bbox      Sidecar index  file.oas.mvi  (on NVMe)
         Layer table: L/D -> name, colour     - per CBLOCK: file offset, comp/uncomp size,
         Instance BVH (GPU LBVH build)          modal-state snapshot, per-layer bbox + count
                        |                     - per layer: density pyramid (tile counts)
                        |                     - per cell: placements summary
                        v                                   |
               View query (camera rect, zoom)  <------------+
                        |
     +------------------+---------------------------------------+
     | zoom out: density pyramid / cell bboxes (no geometry)    |
     | zoom in:  CBLOCKs meeting the view -> inflate (CPU|nvCOMP)|
     |           -> decode -> compact tile (Morton+sid, FOR-128) |
     |           -> LRU host cache -> GPU upload of compact tile |
     +------------------+---------------------------------------+
                        v
        Renderer (GL 3.3 core / EGL headless): per layer one instanced draw;
        the vertex shader decodes compact keys (centre Morton + shape table) to rects;
        trapezoids/polygons from a triangle buffer; outlines in a second pass or shader.
```

### 3.1 Data model in the viewer
- **Tile** = the unit of caching: the decoded geometry of one CBLOCK (or a fixed group of
  CBLOCKs) for one cell, split per layer, stored as a `CompactLayer` (exists) plus a small
  side store for non-rectangles (trapezoid records: 4 int32 + type; polygons: offsets + int32
  vertex pairs). Tiles are immutable and content-addressed by (file id, CBLOCK offset).
- **Caches:** L1 = GPU buffers of compact tiles (budget `MAGVIEWER_GPU_GB`); L2 = host LRU
  (budget `MAGVIEWER_MEM_GB`); L3 = disk cache of compact tiles in the sidecar directory
  (`MAGVIEWER_CACHE_DIR`, default next to the file or `$TMPDIR`), mmap-able, so a second
  open of the same file never re-inflates. Compact tiles are ~3 B/box versus 16 B/box raw,
  so L3 for MW_8x8 10-layer (~4.1B boxes) is ~13 GB.
- **CBLOCK random access:** OASIS modal variables (layer, datatype, width, height, x/y,
  repetition, ...) carry over CBLOCK boundaries, so a CBLOCK cannot be decoded on its own.
  The sidecar stores the modal-state snapshot at the start of each CBLOCK (about 64 B each),
  which makes every CBLOCK independently decodable in parallel. Our own writer (§4) will
  additionally reset modal state at each CBLOCK so even files without a sidecar decode in
  parallel.

### 3.2 Strict-mode use
Strict mode guarantees: table offsets in the END record (or START) point to the CELLNAME,
TEXTSTRING, PROPNAME, PROPSTRING, LAYERNAME and XNAME tables, and names are only in those
tables. With the standard properties:
- `S_TOP_CELL` -> the top cell without a hierarchy walk;
- `S_CELL_OFFSET` on each CELLNAME -> byte offset of each CELL record (random access);
- `S_BOUNDING_BOX` on each CELLNAME -> cell bbox (flags, x, y, w, h), so the instance BVH
  and the first frame need no geometry decode.
Non-strict files fall back to one full scan that builds the same information into the sidecar.
`--verify-strict` will check the claims (offsets land on CELL records, bboxes contain the
decoded geometry) on a sample of cells.

### 3.3 Level of detail
- **Below about 1 pixel per shape** draw the per-layer density pyramid (a 2-level-per-octave
  tile grid of box counts and covered area, built during the scan) as a shaded raster.
  This is what keeps a 10T-shape view interactive.
- **Hierarchy:** an instance whose cell bbox is < N pixels draws as its bbox (filled or
  outline); larger instances recurse. Repetitions expand only inside the view.
- **Geometry mode** when the visible box estimate (from the pyramid) is below the frame
  budget (`MAGVIEWER_FRAME_BOXES`, default 20M on GB10). Above the budget, draw the pyramid
  for the overflow region while tiles stream in (progressive refinement; never block a frame
  on I/O).
- Prefetch: tiles in a one-screen ring around the view are loaded by a background thread pool.

### 3.4 GPU use (each item measured against the CPU path before it becomes the default)
| Work | GPU approach | Fallback |
|---|---|---|
| CBLOCK inflate | nvCOMP batched DEFLATE of all CBLOCKs that meet the view (batches of ≥ 64 MB uncompressed; existing `nvcomp_support.cpp`) | zlib on Grace threads (current default; faster for small CBLOCKs on GB10) |
| Decode to compact | CUDA kernel: OASIS RECTANGLE varint decode is sequential per CBLOCK, so parallelise across CBLOCKs (one warp per CBLOCK), then Morton key + sort with existing Thrust paths | OpenMP over CBLOCKs |
| Instance BVH | LBVH (Karras 2012) over instance-bbox centre Morton codes; keys from `gpu_morton.cu` | existing CPU R-tree |
| Density pyramid | atomics into a tile grid from compact blocks | OpenMP reduction |
| Rendering | compact tile in a GL buffer; vertex shader decodes key → (cx, cy) and looks up (w, h) in the shape table → instanced quad. GPU memory ≈ 3 B/box instead of 32 B/box for quads. | CPU decode to int32 quads (current) |
| Picking | GPU id buffer (render shape ids to an offscreen R32UI target) | spatial query at cursor |
CUDA–GL interop (`cudaGraphicsGLRegisterBuffer`) lets the decode kernel write straight into the
render buffer; on GB10's unified memory this is a zero-copy path.

## 6. Benchmarks
A headless benchmark mode, `MAGVIEWER.exe --bench script.txt file.oas`, rendering through
EGL (no display on this box) to an offscreen framebuffer:
- **Load:** open (tables only), first frame, sidecar scan (first open), sidecar reuse (second
  open), each phase separately: mmap, table parse, CBLOCK inflate (CPU vs nvCOMP), decode,
  index/LBVH build (CPU vs GPU), pyramid build.
- **View:** a scripted camera path: full view → 10 zoom steps to ~2 µm → pan 100 screens east
  → zoom out → random jumps (seeded). Per frame: wall ms, boxes drawn, tiles hit / missed /
  from disk, bytes inflated.
- **Memory:** peak RSS, GPU memory (`cudaMemGetInfo`, since unified memory hides it from RSS),
  cache sizes, system MemAvailable minimum.
- **Correctness:** per-frame hash of drawn boxes compared with a brute-force decode of the
  same window (extends today's `test_viewer_index.exe` oracle); image checksum for the
  renderer.
- **Reference:** KLayout 0.27.8 batch load time and RSS for the same files
  (`klayout -b -r` with an `RBA::Layout` read), noting it is a different (fully loading) design.
Output: one JSON per run plus a CSV summary in `regress/viewer/out/`, and a report page.
Every run goes through the memory watchdog; never two heavy runs at once.

### 7.4 Measurement (ruler)
- Coordinates in database units converted to µm from the START unit.
- Ruler shows dx, dy and Euclidean distance, drawn as a line with end ticks and a label.
- Snap (Shift): nearest box edge or corner within 8 px, found by a spatial query at the cursor.
- Multiple rulers kept until `c`; saved with annotations (§7.5).
- Orthogonal mode (Ctrl) for pure horizontal/vertical CD measurement.

### 7.5 Picking, properties and annotations
- Pick = spatial query at the cursor (topmost visible layer first; repeated clicks cycle
  through overlapping shapes). Result: layer name, L/D, bbox, w×h, shape kind, and its
  OASIS PROPERTY records (e.g. net id, net name, `S_GDS_PROPERTY`).
- Properties are stored sparsely: a map from shape id (CBLOCK offset + index) to property
  list, built during the sidecar scan only for shapes that carry properties.
- Annotations: user notes and rulers attached to a location or shape, saved to
  `file.oas.annot.json` and exportable as an OASIS overlay (TEXT on a chosen layer, with
  PROPERTY records) so other tools can read them.
- Metrology import: a CSV of (x, y, layer, name, value) shown as markers; picking a marker
  shows its values. Net coloring (colour all shapes with the same net id) is a later item.

## 8. Rendering upgrade
- Move from GL 1.x fixed function to **OpenGL 3.3 core** (or GLES 3.1 for EGL headless),
  with a GLFW window when a display exists and an EGL pbuffer otherwise.
- Per layer: one instanced draw of compact tiles (shader decode) + one draw of trapezoid
  triangles; outline in the fragment shader (distance to the rect edge) instead of a second
  pass; per-layer stipple patterns as an option.
- Overlay pass for text, rulers, HUD, selection highlight.
- Fortran keeps the application logic; the GL/EGL shader code lives in a small C file
  (`viewer_gl.c`) with a `bind(C)` API, like `rpc_socket.c`.

## 11. Risks and caveats
- **nvCOMP on GB10:** earlier measurements found Grace zlib faster for typical CBLOCK sizes;
  the GPU inflate path is kept only where measured faster (large batched CBLOCKs).
- **Modal state across CBLOCKs** makes parallel decode of third-party files depend on the
  sidecar scan (one sequential pass per cell stream). Our files avoid this by construction.
- **No display here:** interactive checks need a machine with a display; this box can only
  run EGL headless benchmarks and screenshots.
- **MULTIGON is not a standard OASIS record.** In this repo, `ldb_write_oasis_gear_multigon`
  (`db/oasis_writer.cpp`) writes a "multigon" as several standard POLYGON records: the gear
  outline plus the hole rings on another layer. The viewer will treat a multigon as a polygon
  with holes when the holes are given that way. Curvilinear shapes come in as many-vertex
  polygons, so polygon rendering (triangulation, cached per tile) covers them.
- **Strict files from other tools** may omit `S_BOUNDING_BOX` or use the "bbox unknown"
  flag; then the sidecar scan computes bboxes.
- **10T shapes** are only reachable with hierarchy/repetitions (see §2); flat files top out
  near 4T boxes per TB.
