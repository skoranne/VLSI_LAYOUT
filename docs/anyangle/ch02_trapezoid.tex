\chapter{Exact Integer Arithmetic and Canonical Trapezoid Representation}
\label{ch:trapezoid}

\section{Why Floating-Point Predicates Fail in Planar Geometry}

In computational geometry for VLSI layouts, coordinate values lie on an integer database-unit (dbu) grid, typically $1\text{ dbu} = 1\text{ nm}$ ($1000\text{ dbu}/\mu\text{m}$), spanning full-reticle coordinates up to $\pm 10^8\text{ dbu}$. Computing the orientation of three points $(a,b,c)$ requires evaluating the $2 \times 2$ determinant:
\begin{equation}
  \operatorname{orient2d}(a, b, c) = (b_x - a_x)(c_y - a_y) - (b_y - a_y)(c_x - a_x).
\end{equation}
With 30-bit signed coordinates ($|c| \le 2^{30}-1 \approx 1.07 \times 10^9$), differences reach $2^{31}$, and products reach $2^{62}$. IEEE-754 double precision (\texttt{real64}) provides only 53 bits of significand; two products near $2^{60}$ that differ by $1$ lose their low 7 bits, causing sign flips on near-collinear edges. A single sign flip in a sweep-line tree invariant breaks transitivity of the active-edge ordering, corrupting the entire layer.

\section{Exact 128-Bit Integer Arithmetic (\texttt{WideIntModule})}

Standard Fortran 2008 does not guarantee a native 128-bit integer kind across all compilers (and GPU offload targets on \texttt{nvfortran} require explicit device-callable arithmetic). \texttt{src/wide\_int.f90} therefore implements a portable, branch-minimal, \texttt{elemental pure} 128-bit signed integer type \texttt{type(i128)} annotated with \texttt{!\$omp declare target}:

\begin{lstlisting}[caption={Portable 128-bit signed integer representation and exact product comparison in \texttt{src/wide\_int.f90}.},label={lst:wide_int}]
type, public :: i128
   integer(int64) :: hi = 0_int64   ! signed high 64 bits
   integer(int64) :: lo = 0_int64   ! unsigned low 64 bits stored in int64 bits
end type i128

elemental pure function i128_cmp_prod(a, b, c, d) result(s)
  !$omp declare target
  integer(int64), intent(in) :: a, b, c, d
  integer(int32) :: s
  s = i128_cmp(i128_mul64(a, b), i128_mul64(c, d))
end function i128_cmp_prod
\end{lstlisting}

Every geometric predicate in the engine reduces to exact integer operations over \texttt{i128}:
\begin{itemize}
  \item \textbf{Orientation:} $\operatorname{sign}((b_x - a_x)(c_y - a_y) - (b_y - a_y)(c_x - a_x)) = \texttt{i128\_cmp\_prod}(b_x - a_x, c_y - a_y, b_y - a_y, c_x - a_x)$.
  \item \textbf{Rational $x$-comparison on a scanline $y$:} Two lattice lines with rational $x$-coordinates $n_1/d_1$ and $n_2/d_2$ ($d_1, d_2 > 0$) satisfy $n_1/d_1 \lessgtr n_2/d_2 \iff n_1 d_2 \lessgtr n_2 d_1$, evaluated via a fast \texttt{real64} floating-point filter with an error bound and exact \texttt{i128} fallback whenever $|n_1/d_1 - n_2/d_2|$ is within $8\,\varepsilon_{\text{mach}}$.
  \item \textbf{Exact rounding half-up:} \texttt{i128\_round\_div(x, d)} computes $\lfloor (2x + d)/(2d) \rfloor$ exactly for crossing coordinates in snap rounding.
\end{itemize}

\section{The Canonical Horizontal Trapezoid (\texttt{TrapezoidModule})}

Rather than storing floating-point vertices or arbitrary-precision rational fractions on every trapezoid corner, \texttt{src/trapezoid.f90} encodes each trapezoid side as an \emph{exact lattice line} passing through two integer points.

\begin{definition}[Lattice-Line Side Encoding]
A non-horizontal side (\texttt{type(TrapSide)}) spanning integer rows $y_1 < y_2$ is represented by four 32-bit integers $(a_x, k, dx, dy)$ such that:
\begin{enumerate}
  \item $dy > 0$ and $\gcd(|dx|, dy) = 1$ (primitive direction vector; vertical side has $dx = 0, dy = 1$);
  \item $0 \le k < dy$, defining the \emph{anchor lattice point} $(a_x, a_y) = (a_x, y_1 - k)$ as the highest integer lattice point on the line at or below $y_1$.
\end{enumerate}
At any integer row $y \in [y_1, y_2]$, the exact rational $x$-coordinate on the side is:
\begin{equation}
  x(y) = \frac{a_x \cdot dy + (y - (y_1 - k)) \cdot dx}{dy} = a_x + \frac{(y - y_1 + k)\,dx}{dy}.
  \label{eq:side_x}
\end{equation}
\end{definition}

A horizontal trapezoid (\texttt{type(Trapezoid)}) consists of two integer rows $y_1 < y_2$ and two \texttt{TrapSide} records \texttt{l} (left) and \texttt{r} (right): exactly $10 \times 4 = 40$ bytes of flat, alignment-clean Plain-Old-Data (POD).

\section{The Four Fundamental Invariants (I0--I3)}

Every canonical trapezoid set produced by \texttt{TrapMergeModule} satisfies four strict invariants, verified throughout the test suite (\texttt{test\_wide\_int.exe}, \texttt{test\_predicates.exe}, \texttt{test\_trapmerge.exe}, \texttt{test\_trapbool.exe}):

\begin{invariant}[I0 --- Safe Coordinate Range]
All input coordinates and trapezoid anchors satisfy $|c| \le 2^{30} - 1$. Overflow is never silently wrapped; out-of-range inputs return \texttt{status = 2}.
\end{invariant}

\begin{invariant}[I1 --- Integral Doubled Area]
Although an individual trapezoid's corners may have rational $x$-coordinates (when a horizontal slab cut intersects a slanted boundary edge between two lattice vertices), every vertex of the union polygon lies on an integer lattice point after snap rounding. By Pick's theorem / shoelace summation, twice the total area of any closed region is an exact integer:
\begin{equation}
  2A = \sum_{i=1}^{N} (y_{2,i} - y_{1,i})\bigl(x_r(y_{1,i}) + x_r(y_{2,i}) - x_l(y_{1,i}) - x_l(y_{2,i})\bigr) \in \mathbb{Z}.
\end{equation}
\texttt{trap\_area2} accumulates rational terms per distinct denominator $dy$ and asserts that the fractional remainder is identically zero (\texttt{area\_integral = .true.}).
\end{invariant}

\begin{invariant}[I2 --- Exact Zero-Drift Clipping]
Clipping a trapezoid horizontally to any integer sub-interval $[y_a, y_b] \subseteq [y_1, y_2]$ never rounds coordinates. It simply advances the anchor by $q = \lfloor (y_a - y_1 + k)/dy \rfloor$, setting $a_x' = a_x + q \cdot dx$ and $k' = (y_a - y_1 + k) \bmod dy$. Repeated splits and stitches preserve bit-identical sides.
\end{invariant}

\begin{invariant}[I3 --- Canonical Uniqueness]
A canonical trapezoid set is interior-disjoint, maximal horizontally (no two trapezoids share a side segment) and maximal vertically (no two vertically adjacent trapezoids share the same left and right lattice lines). Consequently, the canonical trapezoid set depends \emph{only} on the planar region---never on input polygon ordering, band count, or OpenMP thread scheduling.
\end{invariant}

\begin{lstlisting}[caption={Exact POD definitions and zero-drift vertical clipping in \texttt{src/trapezoid.f90}.},label={lst:trapezoid_def}]
type, public :: TrapSide
   integer(int32) :: ax = 0, k = 0, dx = 0, dy = 1
end type TrapSide

type, public :: Trapezoid
   integer(int32) :: y1 = 0, y2 = 0
   type(TrapSide) :: l, r
end type Trapezoid

pure function side_at_row(s, y1, y_new) result(sn)
  !$omp declare target
  type(TrapSide), intent(in) :: s
  integer(int32), intent(in) :: y1, y_new
  type(TrapSide) :: sn
  integer(int64) :: t, q, r
  t = int(y_new - y1, int64) + int(s%k, int64)
  q = floor_div_i64(t, int(s%dy, int64))
  r = t - q * int(s%dy, int64)
  sn%ax = int(int(s%ax, int64) + q * int(s%dx, int64), int32)
  sn%k  = int(r, int32)
  sn%dx = s%dx
  sn%dy = s%dy
end function side_at_row
\end{lstlisting}

\section{Exact Trapezoid Overlap and Contact Predicates}

Both \texttt{CONNECT} (\texttt{fascl\_connect.f90}) and polygon topologicals (\texttt{trap\_topo.f90}) rely on exact, device-capable predicates in \texttt{src/trapezoid.f90}:
\begin{itemize}
  \item \texttt{trap\_overlap\_positive(a, b)}: Decides whether the open interiors of convex trapezoids $a$ and $b$ intersect via an exact 2D separating-axis test over the horizontal span $[y_{\min}, y_{\max}]$ and the four side lattice lines using \texttt{i128} orientations. Touching along an edge or point returns \texttt{.false.}.
  \item \texttt{trap\_contact(a, b)}: Classifies the exact set-theoretic intersection $a \cap b$ into four states: \texttt{TC\_NONE} (disjoint), \texttt{TC\_POINT} (0D single point), \texttt{TC\_SEGMENT} (1D positive-length boundary segment, interiors disjoint), or \texttt{TC\_OVERLAP} (2D positive-area interior overlap). Verified by \texttt{test\_trapoverlap.exe} across 900,000 random and degenerate cases with zero failures.
\end{itemize}

\section{Worked Example: Exact Lattice-Line Clipping and Rational Comparison}

To make Invariant~I2 concrete, consider a slanted left side passing through lattice points $(100, 50)$ and $(103, 57)$. Its primitive direction is $(dx, dy) = (3, 7)$ since $\gcd(3, 7) = 1$. Suppose a trapezoid spans $[y_1, y_2] = [52, 65]$:
\begin{itemize}
  \item At $y_1 = 52$, the highest lattice point at or below $y_1$ is $(100, 50)$, so $a_x = 100$ and $k = 52 - 50 = 2 \in [0, 6]$.
  \item The exact rational $x$-coordinate at $y_1 = 52$ is $x(52) = 100 + \frac{2 \times 3}{7} = \frac{706}{7} \approx 100.857142\dots$
  \item Now suppose \texttt{TrapSweepUnion} or a band boundary clips this trapezoid at $y_{\text{cut}} = 60$. Evaluating \texttt{side\_at\_row} gives:
  \[
    t = (60 - 52) + 2 = 10, \qquad q = \lfloor 10/7 \rfloor = 1, \qquad r = 10 - 7 = 3,
  \]
  yielding $a_x' = 100 + 1 \times 3 = 103$, $k' = 3$, with unchanged $(dx, dy) = (3, 7)$.
  \item Checking Eq.~(\ref{eq:side_x}) at $y = 60$: $x'(60) = 103 + \frac{3 \times 3}{7} = \frac{730}{7}$, which equals the unclipped line $100 + \frac{(60 - 50) \times 3}{7} = \frac{730}{7}$ \emph{identically} with zero rounding error!
\end{itemize}

\subsection{Floating-Point Filter with Exact \texttt{i128} Fallback}

Comparing two lattice lines $s_1, s_2$ at row $y$ requires comparing $n_1/d_1$ against $n_2/d_2$ where $n_i = a_{x,i} d_i + (y - y_{1,i} + k_i)\,dx_i$ can reach $2^{62}$. Evaluating the floating-point quotients $f_1 = \text{real}(n_1)/d_1$ and $f_2 = \text{real}(n_2)/d_2$ takes 4 CPU cycles. Whenever
\[
  |f_1 - f_2| > 8\,\varepsilon_{\text{mach}}\,\max(|f_1|, |f_2|, 1),
\]
the floating-point sign is mathematically certified exact. Only in the rare near-tie case ($< 0.01\%$ of comparisons) does the engine invoke \texttt{i128\_cmp\_prod(n1, d2, n2, d1)}, combining floating-point throughput with exact arithmetic certainty.

\begin{lstlisting}[caption={Exact separating-axis interior overlap test (\texttt{trap\_overlap\_positive}) structure in \texttt{src/trapezoid.f90}.},label={lst:trap_overlap}]
pure logical function trap_overlap_positive(a, b) result(ov)
  !$omp declare target
  type(Trapezoid), intent(in) :: a, b
  integer(int32) :: ylo, yhi
  ov = .false.
  ! 1. Open vertical interval intersection: (a%y1, a%y2) cap (b%y1, b%y2)
  ylo = max(a%y1, b%y1)
  yhi = min(a%y2, b%y2)
  if (ylo >= yhi) return
  ! 2. Inside (ylo, yhi), both trapezoids are linear in y:
  !    x_a_left(y) < x_b_right(y) AND x_b_left(y) < x_a_right(y)
  !    has a solution y in (ylo, yhi) iff the 1D linear feasibility
  !    interval (t_min, t_max) subset (ylo, yhi) is non-empty (exact i128).
  ov = side_intervals_overlap_open(a%l, a%r, a%y1, b%l, b%r, b%y1, ylo, yhi)
end function trap_overlap_positive
\end{lstlisting}
